01 / The decision

A bounded fix at the existing boundaries.

This is an appropriate fix for malformed-answer crashes, not a claim that the whole submission system is now fully validated. It reuses the existing request validator and field-validation flow. It does not need a new service, dependency-injection layer, or a second submission pipeline.

What the original PR solved

PR #10332 adds a schema guard inside validateFieldV4, before hidden-field checks, change detection, and optional-answer skipping. Missing attachment values therefore return a validation error instead of reaching .trim().

But this is downstream of attachment scanning and the V4 → V3 adapter.

What the follow-up fixes

Use the same schemas in request validation, which runs before those consumers. Require the attachment filename that scanning copies into the durable answer. Reject multipart enrichment exceptions through the existing error path.

The latest patch also replaces the older checkbox and children shape checks with the shared guard.

A concrete source of the missing value

The scan service sets answer.value = response.answer.filename. If the filename is absent, the server itself can replace a valid quarantine key with undefined. Requiring the filename before scanning prevents that transition. The original production payload is unavailable, so this remains a verified code path, not a proven incident diagnosis.

    03 / Validation ownership

    Define the shape once. Apply it where needed.

    The audit found two competing implementations of the same V4 shape rules. Replacing them with the schema guard fixes drift without merging structural rules with form-specific policy.

    Why checking a shape more than once is intentional here

    The request check protects scanning and logic adaptation. Later, the workflow may insert previously stored responses that never passed through the current request check. Direct validator calls also bypass request middleware. Each entry reuses one rule definition. Eliminating every repeat would require a validated-data type and a wider caller migration; that is more change than this bug needs.

    Why not simply run all field validators earlier?

    Requiredness and visibility depend on form logic; attachment size checks need downloaded content. Running all those rules before scanning or logic would put them before their inputs exist. Shape validation has no such dependencies and can run at the request boundary.

    Why not turn missing values into empty strings?

    A malformed body and a valid empty answer are different inputs. Defaulting a missing value to an empty string could silently skip validation for an optional field. Reject malformed structures first, then let the existing required/optional rules interpret valid empty values.

    05 / Proof & limits

    The reuse patch was driven by failing tests.

    What this evidence does not establish

    The production payload is unavailable. These tests establish the handled code paths, not the incident’s exact origin. No live S3/GuardDuty round trip was performed. A broader database-backed test run stalled during setup; the test-inclusive TypeScript configuration also reports errors outside this patch.

    Remaining architectural limits

    The multipart receiver still enriches loosely typed data; the new catch turns enrichment failures into request errors. Most internal APIs still accept types that imply validation without encoding it. Historical responses can also reach other consumers before validateFieldV4; this work does not claim comprehensive validation or repair of every stored record.

    The general shape map mirrors SDK types and must evolve when the answer protocol changes. Its exhaustive field-type map catches missing field variants, but does not automatically detect every change to a nested SDK type. A future protocol-schema ownership change should address that across callers, not be hidden inside this patch.

    06 / Source trail

    Read the implementation in this order.

    Links below pin the pushed implementation at e9c45b1a6. The checkbox/children reuse follow-up is described separately, because it is not in that commit.

    The reuse patch, in three steps

    validators/checkboxValidator.ts: remove isCheckboxAnswerShapeV4; invoke validateResponseShapeV4 at the start of the chain.

    validators/childrenValidator.ts: remove the manual object/subfield guards; check the field type and invoke the shared guard, followed by childrenAnswerNotEmptyValidatorV4 and the existing domain rules.

    __tests__/response-shape-validator.spec.ts: add four malformed-answer regressions and a field-type mismatch regression for direct calls, so wrapper validation cannot mask a divergent local check.
